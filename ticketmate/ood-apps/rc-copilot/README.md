# RC Copilot — Open OnDemand interactive app

Makes RC Copilot launchable from the OOD dashboard, and **removes the manual
configuration step from the browser extension entirely.**

## Why this exists

The backend runs on whatever compute node Slurm gives you, on whatever port is
free. Both change every allocation, so nothing static can point at them. That
was why the extension originally asked you to paste a URL and a token.

OOD already solves this. For every interactive session it writes a
`connection.yml`:

```yaml
host: c0632
port: 5902
password: <generated>
```

`before.sh.erb` asks OOD for a free port and a generated password;
`script.sh.erb` starts vLLM and rc-copilot using them; `view.html.erb` renders
the session card. Because we own that card's markup, it carries the details in
data attributes:

```html
<div id="rc-copilot-connection"
     data-rc-path="/rnode/c0632/40119"
     data-rc-token="..." hidden></div>
```

The extension's `ood-connect.js` content script reads them and configures
itself. **Opening "My Interactive Sessions" is enough** — OOD renders each app's
view inline on that page, so there is nothing to click and nothing to copy.

### Why not just query OOD for the session list

Checked, and it isn't viable: the dashboard's `batch_connect/sessions#index`
action renders HTML only, with no `respond_to :json`, and `/activejobs/json`
returns one job by id rather than a list. Scraping that HTML would break on
every OOD upgrade. Reading markup we control does not.

## Install (no sysadmin needed)

Sandbox apps under `~/ondemand/dev` appear in the dashboard under **My Sandbox
Apps** once Developer Mode is on — you already run several.

```bash
cp -r ood-apps/rc-copilot ~/ondemand/dev/rc-copilot
```

Then in OOD: **Develop → My Sandbox Apps → RC Copilot → Launch**.

## Files

| File | Role |
| --- | --- |
| `manifest.yml` | Name, icon, category in the dashboard |
| `form.yml` | Launch form: hours, partition, GPU, model |
| `submit.yml.erb` | Slurm directives built from the form |
| `template/before.sh.erb` | Asks OOD for the port and password |
| `template/script.sh.erb` | Starts vLLM (loopback) then rc-copilot (0.0.0.0) |
| `view.html.erb` | Session card + the attributes the extension reads |

## Security

Unchanged from the sbatch route, and slightly better:

- **The token is generated by OOD**, not by us, and lives only in
  `connection.yml` inside the session directory. It never reaches
  `/projects`, which is group-readable.
- **Only the job's owner can see the session card**, so only they can read the
  token — the same model OOD already uses for Jupyter and RStudio passwords.
- **vLLM binds loopback**; only rc-copilot is reachable, and it requires the
  token.
- `ood-connect.js` refuses to save an endpoint that isn't on a
  `northeastern.edu` / `neu.edu` host, so another page can't redirect the
  extension somewhere of its choosing.

The session ends when the job does, which invalidates the URL and the token
together.

## What was verified

Static only — this has not been launched in OOD:

- `manifest.yml` and `form.yml` parse as YAML
- Both `.sh.erb` templates pass `bash -n` with ERB tags stripped
- Every variable `before.sh.erb` exports (`port`, `password`, `VLLM_PORT`) is
  actually consumed by `script.sh.erb`
- The auto-config contract matches exactly: the three `data-rc-*` attributes
  emitted by `view.html.erb` are the three read by `ood-connect.js`, and the
  marker element id agrees on both sides

### Binding rules (learned the hard way)

The three ERB files get **three different bindings**. Mixing them up fails at
staging time with `undefined local variable`:

| File | Binding | How to read a form attribute |
| --- | --- | --- |
| `submit.yml.erb` | form context | bare: `rc_model` |
| `template/*.erb` | `TemplateBinding` | `context.rc_model` |
| `view.html.erb` | connection info | bare `host`, `port`, `password` |

The form attribute is `rc_model`, not `model`, to keep clear of any method of
that name on the context object.

### Confirmed from a working app on this system

`~/ondemand/dev/explorer-ood-apps/vscode/view.html.erb` connects with
`action="/rnode/<%= host %>/<%= port %>/"`. So the `/rnode/` proxy route **is
enabled here** and is the correct one — that was previously the biggest unknown
in the whole design.

Not verified: an actual launch of this app, and whether `partition` as a plain
select is accepted (your other apps use site-specific `auto_queues` /
`new_partitions` widgets). If the launch *form* errors, copy those attribute
names from `~/ondemand/dev/Auxilium/ood-app-auxilium/form.yml`.

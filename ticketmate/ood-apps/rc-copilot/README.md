# RC Copilot — Open OnDemand interactive app

Makes RC Copilot launchable from the OOD dashboard, runs the whole stack in
one GPU job, and lets the browser extension configure itself from the session
card. Members install it with `install.sh` (a symlink to the published
release) — see [../MEMBERS.md](../MEMBERS.md); maintainers release it with
[../publish.sh](../publish.sh).

## What a session runs

`template/script.sh.erb`, in this order (details in
[ARCHITECTURE.md §4.3](../../ARCHITECTURE.md#43-the-ood-app-and-the-session)):

1. **rc-kg** — `rc-kg/scripts/serve_kg.sh`: the graph snapshot loaded into a
   private, node-local Neo4j, its API on loopback with a per-session token.
2. **The backend** on `0.0.0.0:$port`, at once, so the extension can connect
   and show progress while the model loads.
3. **vLLM** on loopback, with the model and context length chosen in the form.

The scripts run TicketMate and rc-kg straight from the checkout
(`ticketmate.env`, written by `publish.sh`, says where it is), so backend and
graph changes need no republish; template changes do.

## How the extension gets connected

The backend runs on whatever node and port Slurm gives the job, so nothing
static can point at it. OOD already solves this for every interactive session:
`before.sh.erb` asks OOD for a free port and a generated password, and
`view.html.erb` renders the session card. Because we own that card's markup,
it carries the details in data attributes:

```html
<div id="rc-copilot-connection"
     data-rc-path="/rnode/c0632/40119"
     data-rc-token="..." data-rc-node="c0632" data-rc-app="RC Copilot" hidden></div>
```

The extension's `ood-connect.js` reads them on *My Interactive Sessions* and
configures itself. OOD has no JSON sessions API (`batch_connect/sessions#index`
renders HTML only; `/activejobs/json` returns one job by id), and scraping its
HTML would break on every upgrade; reading markup we control does not.

## Files

| File | Role |
| --- | --- |
| `manifest.yml` | Name, icon, category in the dashboard |
| `form.yml` | Launch form: hours, partition, GPU layout, model |
| `submit.yml.erb` | Slurm options from the form; enforces partition time and GPU limits; excludes V100 nodes |
| `template/before.sh.erb` | Asks OOD for the backend, vLLM and rc-kg ports and the password |
| `template/script.sh.erb` | Starts rc-kg, the backend, vLLM; waits; cleans up |
| `view.html.erb` | The session card, and the attributes the extension reads |
| `check_modes.sh` | Developer check of the form's model/GPU combinations (not published) |

## Security

- **The token is generated by OOD** and lives only in the session's
  `connection.yml` and on the owner's session card; it never reaches
  `/projects`, which is group-readable. The backend uses it as `AUTH_TOKEN`.
- **Only the job's owner can see the session card**, so only they can read the
  token — the model OOD already uses for Jupyter and RStudio passwords.
- **vLLM and rc-kg bind loopback**; rc-kg also needs its own per-session token,
  because loopback is shared by everyone on the node.
- `ood-connect.js` refuses an endpoint that is not on a `northeastern.edu` /
  `neu.edu` host, so another page cannot point the extension elsewhere.

The session ends when the job does, which invalidates the URL and both tokens.

## ERB binding rules (learned the hard way)

The three kinds of ERB file get **three different bindings**. Mixing them up
fails at staging time with `undefined local variable`:

| File | Binding | How to read a form attribute |
| --- | --- | --- |
| `submit.yml.erb` | form context | bare: `rc_model` |
| `template/*.erb` | `TemplateBinding` | `context.rc_model` |
| `view.html.erb` | connection info | bare `host`, `port`, `password` |

The form attribute is `rc_model`, not `model`, to keep clear of any method of
that name on the context object. The `/rnode/<host>/<port>/` proxy route is
the one enabled on Explorer (the same route the site's VS Code app uses).
